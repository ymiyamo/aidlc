# 単体テストの手順：U1 最小の通し版

## 方針

- 戦略は「標準」：1 つのコンポーネント（Account、Household、Dish、Suggestion）あたり 5〜8 件の単体テストと、主要な境界の統合テスト。通し版には行カバレッジ 80% の下限を適用しない（`team.md`）。ただし、グループの範囲と同時実行の一意性（NFR6.4）のテストは必ず入れる。
- 手法は test-after：層ごとに、実装してからテストを書いて実行する。

## テストの道具と準備

- テスト実行：Vitest（`vitest.config.ts`）。
- データベース：テストは、インストール不要の組み込み PostgreSQL（PGlite）で動く。1 テストファイルごとに空のデータベースを作り、`db/migrations/` を適用する。外部のデータベースやコンテナは要らない。
- 時刻、乱数（候補の順番）、パスワードの変換の強さは、テストでは差し替えられるようにする（テストを速く、結果を決まったものにするため）。

## このユニットだけのテストの実行コマンド

プロジェクト全体のコマンドは使わない。このユニットのテストファイルは、次の場所に置く。

| 層 | ファイル | 実行コマンド |
|---|---|---|
| データモデル／データベース | `src/db/__tests__/schema.test.ts` | `npx vitest run src/db/__tests__/schema.test.ts` |
| リポジトリ | `src/repo/__tests__/*.test.ts` | `npx vitest run src/repo/__tests__` |
| 業務ロジック | `src/domain/__tests__/*.test.ts` | `npx vitest run src/domain/__tests__` |
| API | `src/api/__tests__/*.test.ts` | `npx vitest run src/api/__tests__` |
| 画面 | `src/ui/__tests__/*.test.tsx` | `npx vitest run src/ui/__tests__` |
| U1 全体 | 上の 5 つの場所 | `npx vitest run src/db/__tests__ src/repo/__tests__ src/domain/__tests__ src/api/__tests__ src/ui/__tests__` |

テスト実行の準備（Step 2）が終わるまでは、上のコマンドは動かない。Step 2 で、`npx vitest run` が動くことを確かめ、結果をここに追記する。

## 必ず入れるテスト

| 対象 | 確かめること | 関連 |
|---|---|---|
| メールの一意 | 同時に同じメールアドレスで登録しても 1 件だけ | BR1.2、NFR7.4 |
| 1 人 1 グループ | 同時に 2 つのグループを作っても 1 つだけ | BR2.1、NFR7.5 |
| 選んだもの | 同時に同じ料理を選んでも 1 件だけ | BR4.7、NFR7.6 |
| 初期データ | 同じ出来事を 2 回受けても 30 件のまま。削除した料理が補完で復活しない | BR3.12、NFR7.7 |
| グループの範囲 | 他のグループの料理・選んだものが、読み取り・書き込みのどちらも「見つからない」 | BR2.3、BR2.4、NFR3.5〜3.7 |
| CSRF | Origin または合言葉がない状態変更は拒否される | NFR3.11 |
| 入力 | URL が http/https 以外、料理名が 100 文字超、タグが 6 個、は拒否される | BR3.1〜3.5 |
| 候補 | パスした料理と選んだ料理が出ない。見終えると「見終えました」。ランダムの順番を固定してテストする | BR4.1〜4.5 |
| ログ | パスワード、メールアドレス、料理の URL がログに出ない | NFR4.13 |
| 検証コマンド（通し版） | 登録 → グループ作成 → 保存 → 候補を見て次へ進む が通る | NFR6.3 |

## モック（差し替え）の方針

- データベースは、モックにせず、本物の（組み込みの）PostgreSQL を使う（一意制約の動作を確かめるため）。
- 時刻と乱数と、パスワードの変換の強さだけを差し替える。

## テストデータ

- 初期データは `data/seed-dishes.json` の本物を使うテストと、小さな固定のデータを使うテストに分ける。

## カバレッジの目標

- 通し版そのものには下限を置かない（`team.md`）。測定は行い、`code-summary.md` に数値を記録する。通し版の後の変更には 80% 以上を適用する。
