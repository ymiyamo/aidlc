# 配る仕組みの設計（CI/CD）：U1 最小の通し版

## 根拠（Sources）

- [Q5 A] GitHub Actions。AWS への接続は一時的な権限（OIDC）。`main` へのマージで検証環境に自動、本番は承認ボタンのあと
- [Q6 A] 秘密情報は Secrets Manager 相当
- [Q7 A] まず自分のパソコンで動かす。AWS への実際の作成・配布は別に承認を得る
- [scope] `team.md`（トランクベース、スカッシュマージ、行カバレッジ 80%（通し版の後）、Prettier と ESLint）

## 流れ

1. 作業用ブランチ（短命）で作る。プルリクエストを出す。
2. プルリクエストの確認（自動）：整形と lint（Prettier、ESLint）、型の確認、単体テスト、グループの範囲と同時実行の一意性のテスト（NFR6.4）、構成の差分の表示（CDK diff）。通し版の後は、行カバレッジ 80% 以上を満たす（NFR6.1）。**失敗したらマージできない**（NFR6.2）。
3. `main` へスカッシュマージ（Bolt ごとに 1 コミット）。
4. 自動：ビルド → 検証環境へ配る → 検証環境で、通し版の確認（ログイン → 保存 → 買い物前で候補を見て次へ進む）を自動で行う（NFR6.3）。
5. 本番：承認ボタン（手動承認、技術リードとプロダクトオーナー）のあとに配る。承認のときに、「U7 が未完成なら一般に公開しない」を確認する（NFR3.4、NFR7.10）。
6. 配ったあと：死活と、エラー率のアラームを見る。

## 段階とゲート

| 段階 | 内容 | 合格の条件 | 失敗したら |
|---|---|---|---|
| 確認（プルリクエスト） | 整形、lint、型、テスト、構成の差分 | すべて成功 | マージ不可 |
| ビルド | アプリと画面の部品を作る。小さく保つ（NFR2.5） | 成功 | 配らない |
| 検証環境へ配る | 構成の更新、データベースの移行（スキーマ）、アプリの入れ替え | 死活の確認が通る | 前の版に戻す |
| 検証環境の確認 | 通し版の端から端までの確認 | 成功 | 本番に進めない |
| 本番の承認 | 手動承認 | 承認された | 配らない |
| 本番へ配る | 同上 | 死活の確認が通る | 前の版に戻す |

## 配り方と戻し方

- 配り方：関数の版を切り替える方式（新しい版へ入口を切り替える。問題があれば前の版へ戻す）。通し版では、段階的な切り替え（カナリア）は行わない（数十人の規模）。
- 戻し方：前の版へ切り替える（アプリ）。データベースの変更（スキーマ）は、前の版でも動く形（追加のみ）で行い、戻しても壊れないようにする。データそのものの復元はしない（バックアップなし、F1 B）。
- 環境の昇格：同じ成果物（ビルドの結果）を検証環境から本番へ進める。環境ごとに作り直さない。

## 秘密情報（CI/CD）

- AWS への接続は、一時的な権限（OIDC）で行う。長期のアクセスキーを GitHub に置かない（Q5 A）。
- データベースの接続情報などは、Secrets Manager 相当に預け、アプリが起動時に読む（Q6 A）。CI には置かない。
- 権限は、環境ごとに最小にする。本番への配布の権限は、承認のあとの実行だけに与える。

## ローカルでの確認（Q7 A）

- データベースをコンテナで起動し、初期データとスキーマを入れ、アプリを自分のパソコンで動かす。手順は、README に書く（コード生成）。
- AWS への実際の作成と配布は、この段階では行わない。

## Assumptions & Open Questions

- [assumption] 本番の承認者は、`team.md` の方針（技術リードとプロダクトオーナー）に従う。通し版では、利用者が両方の役を兼ねる可能性がある。
- [assumption] データベースの変更は「追加のみ」を既定とした。質問では聞いていない暫定。
- OQ1 実際に AWS へ作成・配布する時期と、そのときの費用の見積りは、別に利用者の承認を得て決める。

## データベースの移行（スキーマの変更）の実行（レビュー指摘への対応）

データベースは私的なサブネットにあり、GitHub Actions からは直接届かない。そのため、次の形にする。

| 項目 | 決定 |
|---|---|
| 実行する場所 | データベースと同じ仮想ネットワークの中にある、移行専用の関数。アプリ本体の関数とは別にし、データベースの変更権限を持つのはこの関数だけ |
| 呼び出し方 | 配る手順が、移行専用の関数を「呼ぶ」。呼ぶ権限だけを CI の役割に与える（データベースの接続情報は、CI は持たない。移行専用の関数が、秘密情報から読む） |
| 順番 | 構成の更新 → 移行の呼び出し → アプリの入れ替え。移行が失敗したら、アプリは入れ替えず、配る手順を止める |
| 失敗時 | 変更は 1 つの取引で行い、失敗したら元に戻る。データそのものの復元はしない（F1 B）。アプリは前の版のまま動く |
| 形 | 追加のみ（前の版でも動く形）を既定とする |

## 権限の範囲（OIDC と役割）

| 役割 | 引き受けられる条件 | できること |
|---|---|---|
| 確認用（プルリクエスト） | このリポジトリの全ブランチ | 構成の合成と差分の表示だけ。読み取りのみ。AWS のものを変更できない |
| 検証環境へ配る | このリポジトリの `main` ブランチ、かつ GitHub の環境 `staging` | 検証環境の構成の更新、成果物の配置、移行専用の関数の呼び出し、アプリの入れ替え。本番のものには触れない |
| 本番へ配る | このリポジトリの `main` ブランチ、かつ GitHub の環境 `production`（**必須レビュアー＝承認者が承認したあとだけ**実行される保護ルールを付ける） | 本番について、上と同じ。検証環境には触れない |

- 役割は、アプリの関数が実行時に持つ権限（自分のデータベースの接続情報を読む、ログを書く）とは別。
- アプリの関数の権限：自分の環境の秘密情報の読み取り、ログの書き込み、データベースへの接続（アプリ用のユーザー）のみ。表の作成・削除などの変更権限は持たない。
- 「本番の権限は承認のあとだけ」は、GitHub の環境の保護ルール（必須レビュアー）と、役割の信頼条件（環境 `production`）の組み合わせで実現する。

## 通信の許可（セキュリティグループ）

| 通信元 | 通信先 | 許可 |
|---|---|---|
| 配信網 | API の入口 | 許可（秘密の見出しつき） |
| アプリ本体の関数 | データベースの接続の束ね（なければデータベース） | 許可（データベースの 1 つのポートのみ） |
| 移行専用の関数 | データベース | 許可（同上） |
| それ以外 | データベース | 拒否（既定） |

## ローカルで確認できること、できないこと（Q7 A）

| 項目 | ローカル | 備考 |
|---|---|---|
| ログイン、保存、候補、お気に入り、初期データ | できる | コンテナのデータベースで確認 |
| 検証コマンド（通し版の確認、NFR6.3） | できる | ローカルで走らせる。CI の検証環境の確認は、AWS に作ってから |
| 立ち上がりの遅れ（NFR2.5） | できない | AWS に作ってから測る |
| 検証環境の入口の制限、秘密の見出し | できない | 同上 |
| 接続の束ね、データベースの伸縮 | できない | 同上 |

- 接続情報は、リポジトリに入れない設定ファイルに書く（ひな形だけを入れる）。
- AWS の構成コードは、「合成と差分の表示」までを確認する。AWS に実際に作る・配ることはしない。
