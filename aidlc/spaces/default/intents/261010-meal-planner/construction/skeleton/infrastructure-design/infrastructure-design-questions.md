# 動かす基盤の設計（Infrastructure Design）に関する質問：U1 最小の通し版

| 日本語 | 英語 | 意味 |
|---|---|---|
| IaC | Infrastructure as Code | 基盤の構成を、コードで書いて作る・直すやり方 |

A. AWS CDK（TypeScript）で、構成をコードにする（おすすめ）：アプリと同じ TypeScript で書ける。構成の変更も、レビューとテストの対象にできる
B. 画面（コンソール）から手で作る：早いが、再現できず、検証環境と本番がずれる

## Q2. データベースの製品はどうしますか？

A. PostgreSQL 互換のサーバーレス型データベース（Aurora Serverless v2 相当）を使い、使わないときは最小まで縮める（おすすめ）：サーバーレスの「使わない間の費用が小さい」という理由に合う。接続を束ねる仕組み（RDS Proxy 相当）を前に置く
B. 常時起動する通常のデータベース：単純だが、使わない間も費用がかかる

## Q3. アプリ本体をどう動かしますか？

A. アプリ全体を 1 つの関数（Lambda 相当）に載せ、HTTPS の入口（API Gateway と CloudFront 相当）の後ろに置く。画面の部品（静的ファイル）は別の保管場所から配る（おすすめ）：「全体を 1 つのアプリ」という方針に合う
B. 画面とサーバーを別々の関数に分ける：分けられるが、通し版には作業が増える

## Q4. 環境の分け方はどうしますか？

A. 検証環境（staging）と本番（production）の 2 つ。同じ AWS アカウントの中で、構成のコードを共通にし、設定だけを変える（おすすめ）：チームの方針（検証環境へ自動、本番は手動承認）に合う。アカウントを分けるのは、利用者が増えてから
B. アカウントも分ける：安全だが、準備が重い

## Q5. 配る仕組み（CI/CD）はどうしますか？

A. GitHub Actions を使う。AWS への接続は、長期のパスワードではなく、一時的な権限（OIDC）で行う。`main` へのマージで検証環境に自動で配り、本番は承認ボタンのあとに配る（おすすめ）：リポジトリはすでに GitHub にある。秘密の値を持たずに済む
B. AWS の CodePipeline を使う：AWS の中で完結するが、設定が増える

## Q6. 秘密情報（データベースの接続情報など）をどこに預けますか？

A. AWS Secrets Manager（相当）に預け、アプリは起動時に読む。自動の入れ替え（ローテーション）は、通し版では設定しない（おすすめ）：標準的で、コードに値が残らない
B. 環境変数に直接書く：簡単だが、見える場所に値が残る

## Q7. 1st バージョンを最初に触る場所はどこにしますか？

利用者から「あと 1 時間程度で 1st バージョンを触ってみたい」と伝えられています。AWS に実際に作って配ることは、費用が発生し、取り消しにくい操作なので、利用者の許可が要ります。

A. まず自分のパソコンで動かす（データベースはコンテナで起動）。AWS の構成はコード（Q1）までは作るが、実際に AWS へ作る・配ることは、別に承認を得てから行う（おすすめ）：すぐ触れる。費用も発生しない
B. 最初から AWS の検証環境に作って配る：実際の姿に近いが、準備と費用がかかる
