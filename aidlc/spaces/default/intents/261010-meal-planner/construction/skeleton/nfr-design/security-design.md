# セキュリティの設計：U1 最小の通し版

## 根拠（Sources）

- [Q3 A] ログイン状態はデータベースの表に持つ
- [Q4 A] CSRF 対策は、送り元の確認（Origin の照合）と、合言葉（トークン）の両方
- [scope] `security-requirements.md`（U1-NFR3.x）、`rules.md` BR1.x、BR2.3、BR2.4、`decisions.md` ADR-005

## 設計

### 認証

1. 登録とログイン：メールアドレスとパスワードを受け取り、BR1.1、BR1.2 を確認する。パスワードは bcrypt または argon2 相当で変換して保存する（NFR3.1）。
2. ログイン状態：推測できない長いランダム値を発行し、その変換値（元の値ではない）をデータベースの表に持つ。Cookie には元の値を入れる。Cookie は HttpOnly、Secure、SameSite（Lax）、有効期間 30 日（NFR3.2）。
3. ログアウト：表の該当行を削除する。これで、すぐ無効になる（Q3 A）。
4. 失敗の表示：ログインの失敗は、どちらが違うかを区別しない（NFR3.3）。回数の制限は U7（NFR3.4）。

### 認可（リクエストの入口）

```text
リクエスト → [入口] 1. HTTPS か確認
                   2. Cookie → ログイン状態の表 → アカウント
                   3. アカウント → Member（leftAt が空）→ householdId
                   4. 以降の処理に householdId, memberId を渡す
           → [業務] データへの問い合わせは必ず householdId で絞る
```

- 入口は 1 か所にまとめる（ADR-005）。業務の処理は、画面から渡されたグループの値を読まない（NFR3.5）。
- 他のグループの ID は「見つからない」（NFR3.6）。データへの問い合わせの部品は、グループを引数に必須にして、絞らない問い合わせを作れない形にする（NFR3.7）。

### CSRF（Q4 A）

- 状態を変えるリクエスト（POST、PUT、PATCH、DELETE）は、(1) Origin（または Referer）が自分のサイトであること、(2) 画面ごとに発行した合言葉がリクエストに入っていること、の両方を確認する。どちらかが欠ければ拒否する（NFR3.11）。
- 状態を変える操作を GET では受けない。

### 入力と出力

- 入力の検証は、サーバー側の 1 つの検証部品にまとめる。型、文字数、選択肢、タグ数、材料の行を確認する（NFR3.8）。
- URL は、保存のときに http/https だけを許可する。画面でリンクにするときも、もう一度確認する（二重に守る）。新しいタブで開き、情報を渡さない（NFR3.9）。
- 画面に出す文字は、画面の部品の標準の出力（自動で無害化される形）を使い、文字列を直接 HTML として差し込まない（NFR3.10）。

### 通信、秘密、ログ

- HTTPS だけ。HTTP は HTTPS に移す。HSTS（常に HTTPS を使わせる指示）を付ける（NFR3.12）。
- 出来事の受け手（初期データの登録、ホームを開いたときの補完）も、householdId を必須の引数にして、その範囲だけを作る・読む（ADR-005）。入口の確認を通らない呼び出しでも、他のグループには届かない。
- 追加の防御の見出し（セキュリティヘッダー）：内容の種類の固定、枠内表示の禁止、参照元の制限。
- 秘密の値（データベースの接続情報等）は、環境の秘密管理の仕組みから、起動時に読む。リポジトリに入れない（NFR3.13）。
- ログに出さないもの：パスワード、メールアドレス、ログイン状態の値、料理のメモ、料理の URL（NFR3.14）。ログの部品で、これらの項目名を自動で伏せる。
- 初期データのファイルは、リポジトリに入れてよい（ダミーの URL だけ。NFR3.15）。

### 公開の制限（NFR3.4）

- 検証環境の入口は、チームの決まった利用者だけに開ける（入口での認証）。U7 が完成する前に、本番を一般に公開しない。本番の手動承認のとき、この条件を確認する（NFR7.10）。

## 脅威と対策の対応

| 脅威 | 対策の箇所 |
|---|---|
| 他のグループのデータを見られる | 入口の 1 か所化、グループ必須の問い合わせ部品、テスト |
| なりすまし | Cookie の属性、Origin の照合、合言葉 |
| パスワードの流出 | 専用の変換、ログに出さない、秘密管理 |
| 不正な URL・入力 | サーバー側の検証、出力の無害化、リンクの二重確認 |
| 総当たり | U1 では未対応（NFR3.4 の公開制限で補う） |

## Assumptions & Open Questions

- [assumption] セキュリティヘッダーの具体的な値は、コード生成で標準的なものを設定する。
- OQ1 合言葉（トークン）の発行と照合の方式（ログイン状態ごと、画面ごと）は、コード生成で土台の標準機能に合わせて選ぶ。
