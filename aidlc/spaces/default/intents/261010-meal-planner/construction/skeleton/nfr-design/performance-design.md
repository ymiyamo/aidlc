# 性能の設計：U1 最小の通し版

## 根拠（Sources）

- [Q1 A] アプリの中のキャッシュは入れない。データベースの索引だけ
- [Q2 A] 立ち上がりの遅れには特別な備えをせず、軽くして測る
- [scope] `performance-requirements.md`（U1-NFR1.x、U1-NFR2.x）、`rules.md` BR4.1、BR4.3、BR4.10

## 設計

| 対象 | 方針 | 満たす要件 |
|---|---|---|
| 候補の取得 | グループの料理（削除済みと「選んだもの」を除く）を、データベースの 1 回の問い合わせで取り、順番をランダムにして最初の 1 件を返す。見た料理の ID は、除外の条件として渡す（BR4.3）。200 件以下なので、全件を取っても小さい | NFR2.1、NFR2.2 |
| 索引 | 料理は「グループ ID + 削除済みか」で絞る索引を持つ。「選んだもの」は「グループ ID + 料理 ID」の一意の索引。メンバーは「アカウント ID」、ログイン状態は「識別子」の索引 | NFR2.1、NFR7.4〜NFR7.7 |
| 一覧の取得 | 1 回の問い合わせで、料理と材料をまとめて取る（材料を 1 件ずつ取りに行かない）。200 件以下は、分けずに返す | NFR2.1 |
| 書き込み | 保存、お気に入り、「これにする」は、1 回のデータベース操作（1 つの取引）で完了する | NFR2.3 |
| パスワードの変換 | 変換の強さは、1 秒以内（NFR2.4）に収まる範囲で最大にする。測って決める | NFR2.4 |
| 立ち上がりの遅れ | アプリを小さく保つ（使わない部品を読み込まない）、起動時の処理を軽くする（データベースへの接続は、最初に使うときに作る）、画面の初期表示に必要なデータだけを最初に取る。測定は NFR2.5 の方法で行い、守れなければ、利用者に費用を確認してから対策する（Q2 A） | NFR2.5、NFR2.2 |
| 画面 | 最初の候補を先に表示し、次の候補は先読みする（1 件先まで）。スワイプの反応は、画面側で即座に動かし、通信の完了を待たない | NFR1.2、NFR2.2 |
| 画面の軽さ | スマートフォン向けに、画像は使わない（色の枠）。文字と最小限の部品で作る | NFR1.1、NFR2.2 |
| キャッシュ | アプリの中の覚えておく仕組みは入れない（Q1 A）。ブラウザの標準の保存（変更のない静的な部品）だけを使う | NFR2.1 |

## 性能の予算（2 秒の内訳、起動している状態）

| 区間 | 予算 |
|---|---|
| 通信（4G 相当、往復） | 0.5 秒 |
| サーバー（95%） | 0.5 秒 |
| 画面の読み込みと描画 | 1.0 秒 |
| 合計 | 2.0 秒 |

## 画面の対応（NFR1）

- NFR1.1〜NFR1.6 の画面側の設計（横スクロールなし、ボタンの代替、コントラスト、対応ブラウザ）は、コード生成で画面の部品に入れる。コントラスト 4.5:1 は、色の定義を 1 か所にまとめて守る。

## Assumptions & Open Questions

- [assumption] 2 秒の内訳（0.5 / 0.5 / 1.0）は、質問では聞いていない設計上の配分。
- [assumption] 「1 件先まで先読みする」は、質問にない暫定の工夫。既定は「先読みしただけでは、見た扱いにしない」（BR4.3 と矛盾させないため）。コード生成で確認する。
