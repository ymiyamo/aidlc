# 技術スタックの決定：U1 最小の通し版

ここで初めて技術を選びます。質問で聞いたものは「決定」、聞かずに置いたものは「暫定」と書きます。暫定のものは、コード生成か Infrastructure Design で確定します。

## 根拠（Sources）

- [Q1] TypeScript
- [Q2] リレーショナルデータベース
- [Q3] サーバーレス（AWS を想定。Q3 の選択肢 A の説明にある AWS の前提を引き継ぐ）
- [Q10] 対応ブラウザ
- [memory] `team.md`：Prettier と ESLint、CI でのテスト、マージ時の自動デプロイ
- [scope] `unit-of-work.md`：全ユニットを 1 つのアプリとしてデプロイする

## 決定

| 項目 | 選択 | 状態 | 理由 |
|---|---|---|---|
| 言語 | TypeScript（画面もサーバーも） | 決定（Q1 A） | 1 つの言語で全部作れる。入力の型を確認しやすい |
| 実行環境 | Node.js の長期サポート版 | 暫定 | TypeScript のサーバーの標準 |
| 画面とサーバーの土台 | React を使う Web アプリの土台（Next.js を想定） | 暫定 | 画面とサーバーを 1 つのアプリにできる。スマートフォンの画面に向く。コード生成で確定 |
| データベース | PostgreSQL 互換のリレーショナルデータベース | 決定（Q2 A）、製品は暫定 | グループでの絞り込みと、制約（1 件のまま）を守りやすい |
| 動かす場所 | サーバーレス（決定）。全体を 1 つのアプリとして 1 つの関数で動かす。事業者は AWS を想定（暫定） | サーバーレスは決定（Q3 B）、AWS は暫定 | 使わない間の費用が小さい。全体が 1 つのアプリという方針と両立する |
| データベースの接続 | 接続を束ねる仕組みを使う | 暫定 | サーバーレスで接続を使い切らないため（U1-NFR7.9）。Infrastructure Design で確定 |
| ログイン状態の保持 | Cookie に識別子を持ち、データベースに状態を持つ | 暫定 | サーバーが状態を持たない（U1-NFR7.8）。有効期間 30 日、Secure、HttpOnly、SameSite（U1-NFR3.2） |
| パスワードの変換 | bcrypt または argon2 相当 | 暫定（Q8 A の範囲内） | U1-NFR3.1、U1-NFR2.4 |
| 整形と lint | Prettier、ESLint | 決定（`team.md`） | チームの方針 |
| テスト | TypeScript 向けのテスト実行ツール（Vitest を想定）。画面の確認に Playwright を想定 | 暫定 | 通し版の端から端までの確認に使う。コード生成で確定 |
| 初期データ | JSON 等のデータファイル（30 件）。プログラムの外に置く | 決定（`rules.md` BR3.12） | プログラムを変えずに入れ替える |
| CI/CD | マージ時に検証環境へ自動デプロイ。本番は手動承認 | 決定（`team.md`） | チームの方針 |
| ログと監視 | 構造化ログ、死活とエラー率の通知 | 決定（Q7 A、F2 A） | 詳細は `observability-requirements.md` |
| 画像 | 使わない（U6） | — | U1 は色の枠で代える |
| メール | 使わない（U7 で決める） | — | 確認メールは送らない（BR1.4） |

## この選択による注意

- サーバーレスと PostgreSQL の組み合わせでは、立ち上がりの遅れと接続数が課題になる（U1-NFR2.2、U1-NFR7.9）。Infrastructure Design で、方式を確定する。
- 技術を選んだことで、`functional-spec.md` の「技術を決めない」前提を超える。ただし、機能設計の内容（`entities.md`、`rules.md`、`functional-spec.md`）は変えない。
- 他のユニット（U2〜U7）は、この技術スタックを引き継ぐ。ユニットごとに違う言語やデータベースを選ばない。
