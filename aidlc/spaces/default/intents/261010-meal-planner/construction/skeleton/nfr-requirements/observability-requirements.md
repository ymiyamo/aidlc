# 観測の要件：U1 最小の通し版

「動いているか、遅くないか、エラーが出ていないか」を知るための記録と通知です。

## 根拠（Sources）

- [Q7] 構造化ログを残し、エラー率の上昇と応答の遅れを通知する。個人情報をログに出さない
- [F2 A] 通知は「止まった」「エラーが増えた」の 2 つだけ。数値の目標（99% 等）は置かない
- [Q4] 応答の目標（サーバー 95% で 500 ミリ秒以内）

## 要件

| ID | 要件 |
|---|---|
| U1-NFR4.11 | ログは構造化ログ（1 件ずつ、機械で検索できる形）で残す。各リクエストについて、日時、リクエストの識別子、操作の種類、結果（成功・失敗の分類）、処理時間を記録する |
| U1-NFR4.12 | 同じリクエストの記録は、リクエストの識別子でたどれる（グループの識別子も記録に含める。メンバーの識別子は、記録に含めてよいが、名前やメールアドレスは含めない） |
| U1-NFR4.13 | ログに出さないもの：パスワード、メールアドレス、ログイン状態の識別子、料理のメモ、料理の URL。エラーのときも同じ |
| U1-NFR4.14 | 「止まった」を通知する。サービスの死活を定期的に確認し、応答がない状態が続いたら通知する（基準は U1-NFR4.17） |
| U1-NFR4.15 | 「エラーが増えた」を通知する。サーバー側のエラーの割合が上がったら通知する。リクエストが少ないときの誤通知を防ぐため、5 分間のリクエストが 20 件以上のときだけ割合で判定し、それ未満のときは、エラー件数が 5 件以上になったら通知する（基準は U1-NFR4.17） |
| U1-NFR4.16 | 応答の遅れは、通知しない。ただし、処理時間を記録し（U1-NFR4.11）、U1-NFR2.1 の 95 パーセンタイルを、あとから集計できるようにする |
| U1-NFR4.17 | 通知の基準（暫定）：死活は 30 分ごとに確認し、2 回続けて応答なしで通知（最大約 1 時間で気づく）。確認は、データベースに触れない軽い入口で行い、アプリを温め続けない（立ち上がりの遅れの測定と、使わない間の費用を保つため。NFR2.5、Q2 A）。エラー率は 5 分間で 5% 超。実際の運用を見て、Infrastructure Design と運用開始のときに調整する |
| U1-NFR4.18 | 初期データの登録の失敗、データファイルの異常（BR3.12）は、運用者に分かる形で記録する |
| U1-NFR4.19 | ログの保管期間は 30 日（暫定）。それより古いものは消す |

## Assumptions & Open Questions

- [assumption] U1-NFR4.16 は、Q7 A の「応答の遅れを通知する」と F2 A の「通知は 2 つだけ」が食い違うため、後のF2 A を優先し、遅れの通知は置かなかった。遅れの集計はできるようにする。
- [assumption] U1-NFR4.17 の 5 分、5%、U1-NFR4.19 の 30 日は、質問では聞いていない暫定値。
- OQ1 通知先（メール、チャット等）は、Infrastructure Design で決める。
