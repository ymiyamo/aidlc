# 約束事（契約）の決め方に関する質問（Contract Design）

## この段階で決めること

ユニットやコンポーネントが、お互いにやりとりするときの**約束事（契約）**を決めます。契約とは、「何を、どんな形で渡し、失敗したらどうするか」の取り決めです。お店でいえば、厨房とレジの間の「注文伝票の書き方」にあたります。

| 日本語 | 英語 | 意味 |
|---|---|---|
| 契約 | Contract | 境界をまたぐやりとりの取り決め（渡すデータの形、失敗時の扱い） |
| インターフェース | Interface | コンポーネントが外に見せる窓口。呼び出し方の取り決め |
| API | API（Application Programming Interface） | プログラム同士のやりとりの窓口。ここでは、画面（ブラウザ）とサーバーの間が主 |
| REST | REST | 住所（URL）と動作（取る、作る、消す）で窓口を決める、よくある API の形 |
| イベント | Event | 「メンバーが抜けた」のような、起きたことの知らせ |
| 冪等 | Idempotent | 同じ知らせを二度受けても、結果が同じになること |
| 再試行 | Retry | 失敗したときに、もう一度試すこと |
| タイムアウト | Timeout | 待つ時間の上限 |

ここまでの設計から、境界は次の 3 種類です。

1. **画面（ブラウザ）とサーバーの間**：画面が、サーバーに「候補をください」「保存します」と頼む窓口。
2. **コンポーネントの間**：候補の提案が料理に問い合わせる、など（全体を 1 つのアプリとしてデプロイするので、アプリの中のやりとり）。
3. **外部サービスとの間**：画像づくりが生成 AI を呼ぶ、アカウントがメール送信サービスを呼ぶ。

質問ごとに、おすすめの案に **（おすすめ）** を付けました。`[Answer]:` の後ろに選択肢の文字を書いてください。迷う場合は、おすすめで構いません。

## Q1. 画面（ブラウザ）とサーバーの間は、どんな形でやりとりしますか？

A. REST（HTTP と JSON）にする（おすすめ）：もっとも一般的で、調べやすく、テストしやすい。スマートフォンの画面から使える
B. GraphQL にする：画面が必要な項目だけを細かく選んで取れるが、仕組みが複雑になる
C. サーバーが画面（HTML）を作って返す形にする：画面と窓口が分かれず、窓口の取り決めは少なくて済む。ただし、スワイプなど動きの多い画面は作りにくい

## Q3. イベント（メンバーが抜けた、グループが削除された、など）はどう伝えますか？

A. アプリの中の簡単な仕組みで伝える（おすすめ）：知らせをデータベースに記録してから配り、受け手は「少なくとも 1 回届く」「二度受けても同じ結果（冪等）」に作る。届かなかったときは、後から整える。外部のメッセージ基盤は使わない
B. 外部のメッセージサービス（キューなど）を使う：確実で、大きな規模にも向くが、最初の版には大げさで、費用と運用が増える

## Q4. 契約を変えるときのルール（版の管理）はどうしますか？

A. 内部の契約は、同じリポジトリで、同時に直す。画面とサーバーの API だけ、住所に版を付ける（`/api/v1/…`）（おすすめ）：外に公開する API はなく、利用者は自分たちの画面だけ。内部に版を付けても、メリットが少ない
B. すべての契約に版を付ける：将来の分割には安全だが、今は手間が増える
C. 版は付けない：単純だが、あとで画面とサーバーを別に更新したくなったとき、困る

## Q5. 失敗したとき、待つ時間、やり直しはどうしますか？

A. 共通の決まりにする（おすすめ）：エラーは共通の形（種類のコードと、利用者に見せる短い文）で返す。外部の生成 AI は、待つ上限を設け、失敗したら少し間を置いて数回だけ再試行し、だめなら「作成できなかった」として色の枠を出し続ける。メール送信も、同様に数回再試行する。内部の呼び出しは、再試行しない
B. 失敗したらすぐ利用者にエラーを見せ、再試行は利用者に任せる：単純だが、画像づくりが不安定になりやすい
